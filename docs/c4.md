# Modelos C4 — Sistema de Gestión de Turnos para Atención al Cliente

Issue: GES-41 · Entregable: `docs/c4.md` · Se apoya en [`docs/arquitectura.md`](arquitectura.md) (GES-39) y [`docs/componentes.md`](componentes.md) (GES-40)

## 1. Introducción

El modelo C4 describe la arquitectura de un sistema de software en niveles de detalle creciente, como si se hiciera zoom sobre un mapa: primero el sistema y su entorno (contexto), después las piezas que se ejecutan por separado (contenedores) y finalmente los módulos internos de una de esas piezas (componentes).

Este documento presenta los tres primeros niveles para el sistema de Gestión de Turnos. Los diagramas están escritos en Mermaid con notación C4 para que se mantengan como texto editable junto al código. Cada nivel descompone un elemento del nivel anterior: C2 abre el sistema de C1 y C3 abre el servidor Express de C2.

En los diagramas, los elementos en gris y las relaciones marcadas como «previsto» todavía no existen en el código; se muestran porque forman parte del diseño aprobado en GES-40.

## 2. Arquitectura de referencia

GES-39 selecciona una **aplicación web cliente-servidor en tres capas**, con un único servidor y una base de datos local:

| Capa | Tecnología | Ubicación | Responsabilidad |
|---|---|---|---|
| Presentación | HTML, CSS y JavaScript estándar | `src/public/` | Pantallas del cliente, del recepcionista y del administrador, que se ejecutan en el navegador. |
| Aplicación | Node.js y Express (API REST en JSON) | `src/server/` | Atiende las peticiones HTTP, aplica las reglas del negocio (orden de la fila, máximo de llamados, horario, transiciones de estado) y sirve las pantallas. |
| Datos | SQLite con `better-sqlite3` | `database/schema.sql` y `src/server/db.js` | Persistencia de turnos, llamados, servicios, mostradores, horarios y configuración. |

Las pantallas solo se comunican con la API mediante HTTP y JSON, las reglas del negocio viven en el servidor y las operaciones que cambian el estado de un turno se ejecutan en transacciones SQLite.

### 3.1 Explicación

El diagrama de contexto ubica al sistema dentro de su entorno. Hay un único sistema central y tres actores humanos, que corresponden a los roles del modelo de datos (`docs/modelo-de-datos.md`) y de los casos de uso (`docs/casos-de-uso.md`).

- **Cliente:** toma un turno para un servicio, consulta su estado y su espera estimada, y puede cancelarlo mientras espera. No necesita cuenta.
- **Recepcionista:** consulta la fila de su mostrador, llama al siguiente turno, repite el llamado y registra si el cliente fue atendido o no asistió.
- **Administrador:** configurará servicios, mostradores y horarios y consultará reportes. Estas funciones están definidas en los requerimientos (RF-08 y RF-09), pero su pantalla y sus rutas aún no tienen comportamiento.

No se representan sistemas externos porque la solución no se integra con ninguno: todo el estado vive en la base de datos propia del sistema. Las tecnologías, la base de datos y la API quedan fuera de este nivel y aparecen en C2.

## 4. Modelo C2 — Contenedores

**Objetivo:** abrir el sistema de C1 y mostrar las piezas que se ejecutan por separado, su tecnología y cómo se comunican.


### 4.1 Tecnologías y responsabilidades

| Contenedor | Tecnología | Responsabilidad |
|---|---|---|
| Aplicación web en navegador | HTML, CSS y JavaScript sin frameworks | Presentar las pantallas, recibir las acciones del usuario, llamar a la API y mostrar estados y mensajes en español. Guarda en `localStorage` el turno del cliente y el mostrador elegido en recepción. |
| Servidor Express / API REST | Node.js y Express | Servir los archivos de `src/public/`, exponer las rutas `/api/turnos`, `/api/recepcion`, `/api/admin` y `/api/reportes`, validar las peticiones, aplicar las reglas del negocio y responder en JSON con códigos de error claros. |
| Base de datos SQLite | SQLite mediante `better-sqlite3` | Guardar turnos, llamados, servicios, mostradores, horarios y configuración, y conservarlos entre reinicios. |

### 4.2 Relaciones y protocolos

- **Navegador → Servidor Express:** el navegador descarga las pantallas como archivos estáticos y después su JavaScript llama a la API con `fetch` por HTTP, enviando y recibiendo JSON. El panel del recepcionista repite la consulta de la fila cada 2 segundos. El servidor escucha en HTTP; el uso de HTTPS dependería del despliegue y no está configurado en el código.
- **Servidor Express → SQLite:** el servidor ejecuta consultas SQL de forma síncrona con `better-sqlite3`. Las operaciones que cambian el estado (crear, llamar, atender, no asistió) se agrupan en transacciones.

### 4.3 Explicación

Los tres contenedores implementan las tres capas de GES-39: el navegador es la capa de presentación, el servidor Express es la capa de aplicación y SQLite es la capa de datos.

SQLite no es un servidor de base de datos independiente: es una biblioteca embebida que el proceso Node.js usa para leer y escribir el archivo `database/turnos.db` (o el indicado en `DB_PATH`). Se representa como contenedor porque guarda los datos de forma separada y persistente, pero no existe comunicación por red entre el servidor y la base. Por eso, aunque el sistema tiene tres capas lógicas, en ejecución solo hay dos procesos: el navegador de cada usuario y el servidor Node.js.

## 5. Modelo C3 — Componentes

**Objetivo:** abrir el contenedor «Servidor Express / API REST» de C2 y mostrar sus componentes internos, qué hace cada uno y de cuáles depende. Los nombres e identificadores (A1 a A8, D1) son los de GES-40.

Dentro del servidor, los componentes se agrupan en cuatro niveles (entrada, rutas, módulos compartidos y acceso a datos) que siguen el orden de dependencias de GES-40. Esos grupos y los marcos «Capa de presentación» y «Capa de datos» solo ordenan el dibujo; no son contenedores nuevos.

### 5.1 Componentes identificados

| ID | Componente | Responsabilidad | Estado |
|---|---|---|---|
| A1 | Aplicación Express | Crea la aplicación, activa el lector de JSON, sirve `src/public/`, monta las cuatro rutas bajo `/api`, responde 404 en JSON para rutas inexistentes y maneja los errores (400 para solicitudes mal formadas, 500 sin detalles internos). `server.js` la pone a escuchar en el puerto configurado. | Implementado |
| A2 | Rutas de turnos | `GET /servicios`, `POST /` (crea el turno con su número consecutivo del día dentro de una transacción y guarda la espera estimada), `GET /:id` y `PATCH /:id/cancelar` (con token privado cuyo hash se guarda en la base). | Implementado |
| A3 | Rutas de recepción | `GET /fila`, `POST /llamar-siguiente`, `POST /turnos/:id/llamar`, `PATCH /turnos/:id/no-asistio` y `PATCH /turnos/:id/atendido`. Selecciona turnos compatibles con el mostrador, controla el máximo de llamados y calcula la duración de la atención. | Implementado |
| A4 | Rutas de administración | Gestionará servicios, mostradores y horarios. Hoy el archivo solo exporta un router vacío. | Previsto |
| A5 | Rutas de reportes | Entregará los datos de los reportes. Hoy el archivo solo exporta un router vacío. | Previsto |
| A6 | Módulo de estimación | `calcularEsperaEstimada` simula el reparto de la fila entre los mostradores activos compatibles usando la duración de cada servicio (promedio reciente o valor configurado). | Implementado |
| A7 | Regla de horario | `atencionAbierta`, `horarioDeHoy` y `horarioPublico` sobre la tabla `horarios_atencion`. | Implementado |
| A8 | Autenticación | Iniciará sesión de recepcionistas y administradores y verificará su rol. `bcryptjs` y `express-session` están instalados, pero ningún archivo los usa. | Previsto |
| D1 | Acceso a la base de datos | Abre la única conexión a SQLite, activa claves foráneas y el modo WAL, ejecuta `database/schema.sql` y agrega la columna `token_cancelacion_hash` en bases anteriores. | Implementado |

### 5.2 Dependencias

Las dependencias del diagrama salen de los `require` y de las llamadas reales del código:

- `app.js` importa las cuatro rutas y las monta con `app.use`, así que toda petición a `/api/...` entra por A1 y se despacha al router correspondiente. También importa `db.js` para la ruta de diagnóstico `/api/salud`; esa dependencia no se dibuja para no cruzar todo el diagrama.
- `routes/turnos.js` importa `db.js`, `estimacion.js`, `horario.js` y el módulo `crypto` de Node.js. Llama a `calcularEsperaEstimada` dentro de la transacción que crea el turno.
- `routes/recepcion.js` importa `db.js` y `horario.js`. No usa el módulo de estimación.
- `estimacion.js` y `horario.js` importan solo `db.js`.
- `routes/admin.js` y `routes/reportes.js` solo importan `express`.

Las relaciones marcadas «previsto» corresponden a las líneas punteadas del diagrama de GES-40 y no existen todavía en el código.

### 5.3 Explicación

El servidor se organiza en un punto de entrada (A1), un módulo de rutas por área funcional (A2 a A5), módulos compartidos con reglas que usan varias rutas (A6 y A7) y un único punto de acceso a datos (D1). Las dependencias van en un solo sentido: las rutas usan los módulos compartidos y estos usan el acceso a datos; ningún componente inferior conoce a los superiores y las rutas no se llaman entre sí, tal como fijan las reglas de GES-40.

Las peticiones del navegador entran por A1, que sirve las pantallas y despacha cada llamada a la API según su prefijo: la pantalla del cliente termina en A2 (`/api/turnos`) y el panel del recepcionista en A3 (`/api/recepcion`). Es la misma dependencia que GES-40 dibuja directamente de P1 a A2 y de P2 a A3, mostrando además el paso por la aplicación Express. El panel de administración todavía no llama a la API, por eso A4 y A5 solo reciben la relación de montaje desde A1.

GES-40 ubica D1 en la capa de datos. En C4, `db.js` se ejecuta dentro del proceso del servidor, así que se dibuja como componente del contenedor Express, mientras que el archivo SQLite es el contenedor de datos de C2. La responsabilidad es la misma; solo cambia el nivel en que se representa. Las tablas no se modelan como componentes porque son datos dentro del contenedor SQLite.

## 7. Coherencia arquitectónica

**Con GES-39 (arquitectura seleccionada).** C2 reproduce las tres capas elegidas: navegador (presentación), servidor Express (aplicación) y SQLite (datos). Se mantienen las decisiones del documento: un solo servidor, una sola base local, API REST en JSON, reglas en el servidor y consulta periódica en lugar de WebSockets. No se agrega ninguna tecnología ni contenedor que GES-39 no contemple.

**Con GES-40 (componentes, responsabilidades y dependencias).** C3 usa los mismos componentes de la capa de aplicación y de datos (A1 a A8 y D1), con sus nombres, responsabilidades, estados y dependencias, incluidas las previstas. Los componentes de presentación (P1 a P4) quedan agrupados en el contenedor «Aplicación web en navegador» de C2, porque C3 solo descompone el servidor.

**Con la implementación.** Cada componente implementado de C3 corresponde a un archivo real y cada relación a un `require` o una llamada verificada en el código. Se encontraron estas diferencias entre los documentos y el código, que se registran sin modificar GES-39 ni GES-40:

- GES-39 muestra «Reglas del negocio» como un bloque separado de la API. En el código, y en GES-40, esas reglas están dentro de cada módulo de rutas y en los módulos compartidos `horario.js` y `estimacion.js`. C3 sigue la organización de GES-40. GES-39 menciona la separación en una capa de servicios como evolución futura.
- GES-39 indica que las pantallas consultan la API cada 2 segundos y la página de inicio lo anuncia, pero en el código solo lo hace el panel del recepcionista (`setInterval` en `js/recepcion.js`). La pantalla del cliente consulta su turno al abrirse y no se actualiza sola. Por eso C2 y C3 atribuyen la consulta periódica solo a recepción.
- La lista de archivos de GES-39 (sección 2.3) no incluye `estimacion.js`, que se agregó después. GES-40 sí lo incluye.
- `db.js` incluye una migración para agregar `token_cancelacion_hash` en bases creadas antes de la cancelación con token; GES-40 no la menciona, pero no cambia la responsabilidad de D1.

## 8. Conclusión

Los tres modelos permiten entender el sistema de lo general a lo particular. C1 muestra quién usa el sistema y para qué, sin tecnicismos; C2 explica con qué tecnologías se construye y cómo viajan los datos entre el navegador, el servidor y la base; y C3 muestra cómo está organizado el servidor por dentro y qué depende de qué.

Esta vista facilita el mantenimiento y el trabajo en equipo: ubica rápidamente dónde debe hacerse un cambio, deja visibles los componentes pendientes (administración, reportes y autenticación) y sus dependencias previstas, y permite comprobar que las nuevas funciones respeten las reglas de dependencia antes de escribir código. Al estar en Mermaid, los diagramas se actualizan en el mismo repositorio y en el mismo Pull Request que el código que describen.
